# Scheduling mutation scenario

This is a local component scenario, not a whole-package or CI qualification. Base revision `eb2aa8e1d63af84ba3c3879374e9d70671562f7c`; `src/pytest_parallel/scheduling.py` Git blob `03f85231abd5b545b081a527056a46617c7482da`. macOS arm64, CPython 3.15.1 for mutation, pytest 9.2.0, mutmut 3.8.1. The runtime source was not edited. The mirror serves `mutmut-3.8.1-py3-none-any.whl` with Python >=3.10 and BSD-3-Clause metadata, and advertises Python 3.15. A scratch environment was installed exclusively from `https://pypi.17166969.xyz/current/simple/`; no dependency or lock file was changed.

Run with mutmut 3.8.1 and pytest installed in the same environment, with `mutmut` on PATH (or `MUTMUT` set to its executable): `make mutants-scheduling`. The helper makes a new copy under `.work/tmp`, imposes a 20-minute deadline and runs one mutation worker. Campaigns sharing a host must provide their own external CPU cap and lock. The helper verifies its source fingerprint because mutant numbers can move; a source edit requires a new classification. It fails for unclassified or unexpected results and reconfirms timeouts with a longer limit. Generated files stay in the copy. This target is not a diff gate.

The copied configuration uses `source_paths = ["src"]`, `pytest_add_cli_args = ["-p", "no:parallel"]`, and `pytest_add_cli_args_test_selection = ["tests/test_partition.py"]`. `mutmut run --max-children 1 'pytest_parallel.scheduling.*'` generates the package inventory but executes only the named module. `mutmut results --all true` supplies individual classes; the other package identities remain unclassified and outside this scenario. The in-process tests import the module directly; subprocess CLI tests can import a different installation. The installed tool's `configuration.py:144-155` reads these settings, `utils/file_utils.py:80-92` places the generated source first, and `__main__.py:809-815` uses fnmatch on complete names. Its default run exit alone does not certify results.

Before the additions, 276 scheduling identities were selected from 3,547 generated package identities: 87 killed, 19 survived, one timeout, 169 no tests; all others were outside the selection. After additions: 264 killed, 11 survived, one timeout, zero no-tests or suspicious results. The timeout is `x_merge_units__mutmut_4`, which changes `parent[idx] != idx` to `==`: roots loop forever. It timed out again with `timeout_multiplier = 30.0` and `timeout_constant = 2.0`, compared with defaults 15 and 1. The ordinary `mutmut run` outer exit was 0 in each run, including the run with survivors; the results are not inferred from that exit. The remaining 3,271 identities were not evaluated here.

All names below have prefix `pytest_parallel.scheduling.`. The 11 survivors are equivalent for the controller's reachable inputs:

- `x_merge_units__mutmut_12`, `_13`, `_14`: union picks either root or changes `<` to `<=` under `ra != rb`; either root preserves the same connected components, and the later file-order scan constructs the output. This does not claim equal performance.
- `x_assign_units__mutmut_11`, `_13`: pin sorting by index equals sorting by ordinal because the coordinator builds file ordinals in collection order and `merge_units` emits first-seen components in that order (`coordinator.py:234-268`).
- `x_assign_units__mutmut_50`, `_51`: round-robin updates a load that is never read on that branch.
- `x_plan_dict__mutmut_51`, `_53`, `_55`, `_56`: the default of the identity lookup is unreachable: `_build_plan` passes the same `units` to assignment and the plan (`coordinator.py:225-230`), and the buckets contain those unit objects.

The controller accepts positive finite weights, builds contiguous file ordinals, and resolves valid pins before assignment. Malformed internal `Unit` collections are not treated as public input. No survivor is justified by ignoring observable group, weight, tie or pin behavior.

Activation control: using the generated source in the same test process, `MUTANT_UNDER_TEST=''` loaded `mutants/src/pytest_parallel/scheduling.py` and `test_count_balance_assigns_largest_files_first_and_preserves_order` passed (exit 0). With `MUTANT_UNDER_TEST=pytest_parallel.scheduling.x_assign_units__mutmut_30`, the same path loaded and the same test failed its bucket assertion (exit 1): this mutant sorts `+unit.weight` instead of `-unit.weight`, putting `small_a.py` where `heavy.py` was expected. This is a semantic negative control, not an import or compile failure. New literal tests cover validation and diagnostics, transitive merge metadata, pinned plans, accumulated weights, text output and very small positive weights. The scenario does not address the separately deferred DSLP-6.

Limitations: this is one macOS run, not Linux or a supported whole-change CI selection; the wider test audit and DSLP-4 remain open. The external fleet tools document still incorrectly says pytest-parallel has no coverage support; native worker coverage is established in [coverage evidence](deslop-coverage.md).

To reproduce the activation check, set `COPY` to the mutation workspace printed by the target and `MUTMUT_PYTHON` to the Python in the mutmut environment, then run the following twice: first with the empty value shown, then with `MUTANT_UNDER_TEST=pytest_parallel.scheduling.x_assign_units__mutmut_30`. The second run must fail the bucket assertion.

```sh
cd "$COPY/mutants"
PYTHONPATH="$PWD/src" MUTANT_UNDER_TEST='' "$MUTMUT_PYTHON" -c 'import pytest_parallel.scheduling as s, pytest; print("LOADED", s.__file__, flush=True); raise SystemExit(pytest.main(["-p", "no:parallel", "tests/test_partition.py::test_count_balance_assigns_largest_files_first_and_preserves_order", "-q"]))'
```

The source tree was built twice with `TMPDIR="$PWD/.work/tmp" UV_PYTHON_DOWNLOADS=never cpu-guard --cores 2 -- uv build --wheel --out-dir .work/tmp/wheel-before` and the corresponding `wheel-after` directory. `cmp` exited 0: each wheel was 31,199 bytes, and wheel metadata contained only `Requires-Dist: pytest>=9.0`. The tool environment was scratch-only; there is no new project dependency or lock resolution. These sizes describe this build, not a comparison to the earlier coverage worker's different build environment.

Fault controls used a separate scratch copy of `src` and `tests`, serial pytest and one temporary edit per run; each was restored. All six named tests failed with exit 1 at their intended assertions: uppercase group names (`test_scheduling_validation_contract`), zero shard weight (`test_merged_units_preserve_shard_metadata`), zero total plan weight (`test_count_assignment_honors_pins_and_plan`), replace accumulated count load with the latest weight (`test_count_accumulates_loads_for_pinned_and_unpinned_units`), semicolon group separators (`test_text_plan_lists_all_groups_and_files`), and initial loads of one (`test_count_balance_preserves_small_positive_weights`). The scratch harness exited 0 after all six expected failures. Its first attempt stopped after the first three because its replacement string occurred twice; the corrected replacement selected the count branch and the full set was rerun.

The final target, run with `MUTMUT` pointing at the scratch environment under `cpu-guard --cores 2` and the campaign's exclusive lock, exited 0 after 93.67 seconds wall, including confirmation of the timeout. The 20-minute outer timeout also exited 0. The target lists every selected identity and its raw class. The test file Git blob is `050ff5a792bbd07ca31fd26af01e08aee3f9aadc`.

Warm cost observations: a fresh archive of the base with the same unchanged runtime source and locked project environment ran `perf-gate-ready`, `/usr/bin/time -p cpu-guard --cores 2 -- make test`, and immediately `perf-gate-ready -1`: all exit 0, 120 passed, 7.51 seconds wall. The final worktree ran the same sequence: all exit 0, 126 passed, 7.52 seconds wall. The final `cpu-guard --cores 2 -- make lint` exited 0, Ruff and ty passed. Both gate sequences emitted hot-process diagnostics despite their zero exits; these individual observations are noisy, not a speed claim. No production code changed, so no new runtime performance or consumer claim follows.
